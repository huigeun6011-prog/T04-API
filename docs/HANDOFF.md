# 다음 AI를 위한 인수인계

기준: 2026-11-16. 이 문서를 먼저 읽고 [README](../README.md), [방법론](AI/METHODOLOGY.md), 필요한 상세 보고서를 읽는다. **실험·재학습·모델 교체·웹 수정은 사용자 지시가 있을 때만 한다.** 2026-11-16 사용자 지시로 정답 추정 격차 진단(§6)을 마쳤고, 대기열·정원 모델 실험도 마쳤다([queue_model](../outputs/diagnostics/queue_model/report.md), 결과는 §6). 둘 다 production에는 적용하지 않았다.

## 1. 목표와 확정한 요구

- 대전 1호선으로 이동할 때 덜 붐비는 시간·이용 역·목적지를 추천한다. 모델은 장소 자체의 방문객 수를 예측하지 않는다.
- 지도는 Kakao Maps, 주소 좌표 변환은 VWorld다. `best_model.pt`는 이전 모델이고 공식 추론 파일은 `outputs/load_predictor.joblib`이다.
- 실제 POI와 Open-Meteo 날씨를 사용한다. 날짜 선택 시 시간별 날씨를 조회하고 캐시·호출 간격으로 중복 호출을 줄인다.
- 사용자가 출발점·운행일·시간 범위·카테고리·한산함/거리 비중을 고른다. 비중은 10% 단위다. 각 시간 h는 h:00~h+1:00 구간이다.
- 전체 재학습 범위는 **2024-11-01 05시~2026-11-02 00시 버킷**이다. 운행일로는 2024-11-01~2026-11-01, 731일이다. 마지막 00시 버킷은 00:00~00:59에 해당하며 00:00 한 순간을 뜻하지 않는다.
- 출발 승차 전 0은 고정한다. 종점 0·음수 억제는 **soft penalty**로 유지한다. 종점 0을 강제로 맞췄다는 사실을 물리적 성공으로 해석하지 않는다.
- 실제 피크 사례는 validation only다. 학습 라벨·손실 가중치·튜닝 근거로 쓰지 않는다. 시간표 미매칭 1건은 사용자가 이번 비교에서 무시하도록 했다.
- 축제 등 비정규 운행일을 제외하자는 기존 요구가 있지만 **제외 목록 확정·실제 학습 제외는 아직 하지 않았다**. 잔차만 보고 임의로 날을 지우지 않는다.
- 사용자는 메인 AI가 지휘하고 작업은 다른 에이전트에게 맡기길 원한다. 기존 에이전트를 재활용하고 완료·중요 결과를 root에게 직접 보고한다. 사용자는 작업 중 root와 계속 대화할 수 있어야 한다.
- `.env`, API 키 값은 출력·문서화·프런트 전달하지 않는다. 과거 키 노출 후 사용자가 재발급했다. 키 이름과 설정 여부만 다룬다.

## 3. 달력 날짜와 운행일

승하차 API는 실제 달력 날짜 기준이다. 23:50 출발 열차가 다음 날00:10까지 운행하므로 재차인원 궤적은 운행일을 따라 연속으로 계산한다.

| 요청/입력 | 모델·시간표 날짜 | 날씨/승하차 실제 날짜 |
|---|---|---|
| D일05~23시 | D 운행일, 해당 hour | D일 해당 시각 |
| D 운행일24시 | D 운행일, hour=24 | D+1일00시 |
| 달력 D일00시 단일 예측 | D−1 운행일, hour=24 | D일00시 |

요일·휴일·시간표 버전은 운행일을 기준으로 한다. `predict_load.py --hour 0`과 `/api/predict`는 전날24시로 변환한다. 웹 `/api/recommend`는 사용자가 고른 **운행일**과05~24시 범위를 받는다. 01~04시 승하차 자료는 정제 시 제외되어 있고 24시에 합쳐지지 않는다. 과거 AI가 01~04시를24시에 합쳤다고 말한 것은 잘못된 설명이었다.

24시 날씨를 운행일 당일00시에서 가져오던 오류는 수정됐다. 전체 재생성 때 24시18,035행의 날씨가 익일00시와 일치함을 확인했다. 날씨는 GT 최적화 손실에 들어가지 않고 최적화 후 지도학습 피처로 붙는다.

## 5. 수렴 진단과 세 가정 실험

[수렴 결과](../outputs/diagnostics/gt_convergence.json): 대표6일×200/500/1000회 및 초기값2종. 200→1000회 손실이4.47~14.17% 줄지만 종점·음수 위반이 남았다. 반복수만 늘려 해결됐다고 판단하지 않았다.

[3가정 보고서](../outputs/diagnostics/assumption_ablation/report.md): 동일6일×기본/시간정규화/동요일pooling/승차headway/전부×초기값2종×1000회, 총60회·약115초. 구성·seed·template source hash·평가일을 저장했다.

- 시간정규화: p/q 인접 차이에 Huber soft penalty. 큰 출퇴근 변화 허용, 강제 평탄화하지 않는다.
- 동요일 pooling: 월~일7종+명시 공휴일 별도, 시간표버전 분리. 과거112일·동일그룹만 사용, 평가6일 전체 제외. 최소2일, confidence=n/(n+4). 미래/평가일 값을 바꿔도 template 불변 검사를 통과했다. template 자체도 기존 추정 비율의 평균으로 실측값이 아니다.
- headway: **승차만** 직전 시간표 출발~이번 출발 구간에 비례시킨다. 시간 내 균등 입장을 가정하며 실제 대기시간 관측이 아니다. 첫차는05시부터, 시간 경계를 넘은 승차는 `boarding_sources`로 원본 시간별 기록, 마지막 운행 후 입장 가정량은 slack. 하차에 같은 가정을 적용하지 않았다.
- 정상5일 평균 종점MSE: 기본539.62/시간정규화541.72/pooling541.91/headway1107.80/전부1147.53. 음수MSE: 기본12.14/전부53.10.
- 시간정규화는 인접 변화량26.3% 감소, pooling은 template 거리45.3% 감소. 다만 물리 잔차가 전반 개선됐다는 뜻은 아니다. 전부 적용은 평일3일 악화·토요일2일 개선이다.
- 자정 이상 가능일의 잔차 감소는 마지막차 이후 균등입장 가정상 slack 증가가 크게 설명한다. 실제 운행·실제 인원 개선 증거가 아니다.
- 변수는 계속 하루800개(731일584,800개)다. 부분공유를 넣었다고 일별 변수가 없어지지 않는다. 1000회 중앙 실행시간 기본1.67초/전부2.25초였다.
- 세 가정은 코드 옵션으로 구현했지만 기본 활성화·전체 all 재학습·production 교체는 하지 않았다. **baseline 대비 smooth+pooling 두 개만 묶은 실험과 가중치 탐색은 아직 안 했다.** 다음 권고안일 뿐 실행 승인으로 간주하지 않는다.

## 6. 실제 피크와 정확도 해석

(d)20사례 중 출발역·시각·방향·운행일·최고혼잡역으로19건을 연결했다. 2026-08-18 하행1171열차는 시간표 미매칭이며 사용자가 이번 비교에서 무시하도록 했다. 임의로 다른 열차에 맞추지 않는다.

- production 모델MAE375.99명, 라벨MAE312.52명.
- 배분 개선 후보 모델MAE374.45명, 라벨MAE324.88명.
- 선택된 극단 사례이고 전체 학습기간의 날짜도 포함하므로 일반적인 독립 holdout 정확도가 아니다. 모두 과소추정하는 큰 괴리가 남았다.
- 실제 재차인원의 **출발 전/후 측정 정의는 공식적으로 확인되지 않았다**. 사용자는 우선 출발 후 값으로 보고 작업하자고 했다. 이 작업 가정을 실측 정의 확정으로 쓰지 않는다.
- 모델의 실제 정확도, 운영시간별 추천 순위의 타당성, 장소 한적함은 확보되지 않았다. 물리 loss·추정 라벨 MAE가 좋아져도 이 결론은 바뀌지 않는다.
- **격차 진단(2026-11-16, 진단 전용)**: [feasibility_bound](../outputs/diagnostics/feasibility_bound/report.md). 매칭 19건에서 실제 피크(604~717명)가 "그 열차 한 대가 그 시간 승차를 모두 태운다"는 느슨한 상한(4,715~7,997명)을 넘는 사례는 0건이므로 승하차 자료의 계수 부족을 시사하는 증거는 없었다(다만 이 상한은 매우 느슨해 강한 증거는 아니다). 방향 50:50·하차 무시 가정의 균등 배분 기준 대비 실제는 1.20~2.58배(평균 1.88)이고, 현 라벨은 실제의 0.42~0.61배(평균 0.53)로 이 균등 배분 수준에 가깝다. 같은 역·시간·방향 열차를 균등 배분하는 구조([A-002](ASSUMPTIONS.md))가 열차별 편차를 만들지 못한다는 해석과 부합하지만 **확정은 아니다**. 승하차 자료에 방향 구분이 없어 50:50은 가정이고, 하차를 반영하지 않아 필요한 집중도는 이보다 클 수 있다(하한). 하차를 반영한 조임 상한은 방향이 섞여 신뢰할 수 없다. 피크 사례는 진단에만 썼고 보정·튜닝에 쓰지 않았다. 이 결과로 승하차 자료가 틀렸다고 판단하지 않는다.
- **대기열·정원 모델 실험(2026-11-16, 실험 전용, 폐기 권고)**: [queue_model](../outputs/diagnostics/queue_model/report.md), 코드 `scripts/data_prep/gt_queue_model.py`. 도착을 시간 내 균등으로 보고 열차마다 정원만큼만 태우며 못 탄 승객을 이월하는 모델이다. 정상 5일 평균 종점 MSE는 기본 539.8, headway 1108.2, 대기열(정원 475) 1118.1이고 정원 713·950은 headway와 같아 정원 제약이 거의 작동하지 않았다(정차당 최대 승차 약 200명). 정원은 상한만 줄일 수 있어 집중도를 만들지 못한다. 자정 이후 운행 가능일의 오차 감소는 slack(승차 98→4,358) 증가가 설명한다. 사후 피크 비교(19건, 보고만)에서 추정/실제 평균은 기본 0.51, headway 0.30(MAE 465, 악화), 대기열 475 0.47, 필요한 집중도 평균 1.87에 아무도 못 미쳤다. 정원 475는 혼잡도 자료의 재차인원/혼잡도% 상수(약 4.75)에서 도출한 값이라 피크 자료의 열 정의를 본 뒤 정했다는 점에서 약하게 피크 정보가 섞였다. 1000회 1실행에 약 80초(기본은 약 3초)다. **headway 단독도 피크를 더 나쁘게 하므로 헤드웨이 확장이 격차 해소 경로가 아니다.**

## 7. 웹 구현과 중요한 미해결 항목

- `web/app.js`는 `web/data/pois.json`548행을 읽는다. 좌표532개, 좌표 없는 산책로11개는 텍스트로 보여준다. 문화시설0개, 도서관1개·서점4개는 좌표가 없다.
- `web/weather-client.js`: Open-Meteo 무키, 500ms 지연합치기·요청중복제거·최소10초 간격·예보1시간/과거7일 캐시. 익일00시용 다음 날짜도 조회한다. 표시 날짜만 바꿔도 API 추천을 자동 반복하지 않는다.
- `prediction_api.py`: Python 표준 HTTP 서버. `/api/health`, `/api/stations`, `/api/predict`, `POST /api/recommend`. FastAPI나 ONNX 구현이 아니다.
- 추천은 출발점의 최근접역과 장소의 최근접역을 붙이고, 선택 시간에 실제 시간표상 가능한 열차/이동구간을 찾는다. 구간 출발 후~하차 전 정차 예측의 평균·최대를 계산한다. 같은 역+시간에는 평균이 가장 작은 열차를 선택한다.
- 거리 점수는 출발점→장소 직선거리, 한산함은 후보군 최대 평균load 대비 역전값이다. 10% 가중합으로 정렬한다. 같은 역 주변 장소는 열차를 안 타므로 한산함 중립값을 적용한다. 이 중립값·정규화·시간별최적열차 선택이 사용자에게 검증된 최종 정책은 아니다.
- 운영시간·실제 도보경로/시간 자료가 없다. API 성공·점수 계산 가능과 추천 품질을 혼동하지 않는다.
- **좌표(해소됨):** 이전에는 [VWorld 보정표](AI/STATION_COORDINATES.md)와 `app.js` 22개 좌표가 전부 달랐으나(예: 반석 코드36.4029/127.2990), 이후 `app.js`가 보정표 값으로 교체되었다. 2026-11-16 문자열 대조에서 22개 모두 일치를 확인했다. API도 `app.js`를 읽으므로 최근접역·거리 계산에 반영된다. 단, 실제 지도 표시는 브라우저로 확인하지 않았다.
- **저장소 정리(2026-11-16):** `.gitignore`에 `__pycache__/`, `.venv/`, 대용량 CSV, `best_model.pt`를 추가하고 `outputs/ground_truth_train_loads.csv`(380MB), `best_model.pt`, `.pyc`를 git 추적에서 뺐다(파일은 디스크에 있다). production CSV는 저장소에 없으므로 위 SHA256으로 같은 파일인지 확인한다. `load_predictor.joblib`은 API 실행에 필요해 추적을 유지한다.
- `extract_train_loads.py`는 아직 출력 종점을0으로 덮어쓴다. 개선GT의 raw잔차 정책과 다르다. 다음날 날씨를 중복 로드하는 코드도 있다. 추출 JSON을 raw 물리 검증에 쓰지 않는다.
- API 실제 응답과 JS 문법/연결 확인까지 했다. 브라우저 접근이 이전에 거절되어 지도 위치·클릭·전체 UX의 시각검증은 하지 않았다. 이후 브라우저 검증도 없다. 기존 거절을 우회하지 않는다.
- SVG는 데이터 구조 설명 자료이며 현재 실험·배포 상태의 정본이 아니다. 이번 요청에서는 SVG를 수정하지 않았다.

## 8. 실행 환경과 상태 확인

프로젝트 루트에서 `.venv/Scripts/python.exe`를 쓴다. 기본 시스템 Python3.15에는 torch가 없어 Python3.12 환경을 만들었다. production metadata 당시 Python3.12.16, torch2.15.0+cpu, scikit-learn1.9.1이다. 완전한 의존성 lockfile은 아직 없다.

```powershell
# 먼저 포트 상태를 확인한다. 이미 실행된 서버를 중복 시작하지 않는다.
Get-NetTCPConnection -LocalPort 8000,5500 -State Listen -ErrorAction SilentlyContinue
Invoke-RestMethod http://127.0.0.1:8000/api/health

# API가 없을 때 별도 터미널에서 시작
.venv/Scripts/python.exe prediction_api.py --port 8000

# VS Code Live Server 대신 정적 서버가 필요할 때 다른 터미널에서 시작
.venv/Scripts/python.exe -m http.server 5500 --bind 127.0.0.1
```

페이지는 `http://127.0.0.1:5500/web/index.html`이다.8000은예측API용이다. CORS는5500의localhost/127.0.0.1을허용한다. 현재 프로세스가 실행 중이라는 상태는 시간이 지나면 바뀌므로 이 문서만 보고 가정하지 않는다. 재시작은 해당 서버 터미널에서 종료한 후 같은 명령으로 한다.

## 10. 다음 AI가 먼저 할 일

1. 현재 사용자 지시가 무엇인지 확인한다. 새 실험·재학습은 사용자 지시가 있을 때만 한다. 진행 중인 에이전트는 없다. 이전 `ml-gt` 에이전트의 맥락은 세션 밖으로 이어지지 않으므로 새로 시킬 때는 이 문서와 §6 진단 보고서를 읽히고 시작한다.
1a. **다음 실험 후보(미실행, 사용자 합의 전):** 사용자가 직접 제안한 "승차 후 한 정거장만에 하차할 확률은 낮다" 가정을 반영하는 트립 길이 prior(OD/승객 집단 구조). 현재 구조는 하차가 누가 어디서 탔는지와 무관해(`A·q/n`) 이 가정을 넣을 자리가 없다. 하차를 하류로 옮겨 중간 구간 재차인원의 **전체 수준**을 높일 가능성이 있으나 효과 크기는 미확인이다. 하강 모양 2~3개를 피크 사례를 보기 전에 정하고, 같은 6일·1000회·같은 시드로 비교하며, 피크 19건은 마지막에 사후 보고만 한다. 대기열·정원 모델과 headway 확장은 §6 결과로 후보에서 제외했다.
1b. 사용자는 "승하차 자료가 잘못됐다"고 보지 않기로 했고(진단에서도 그 증거는 없었다), 다른 지역 자료로 알고리즘을 검증하는 방안(A)은 하지 않기로 했다. 재차인원 측정 시점 확인과 Kakao 콘솔의 키 보호 조치도 하지 않기로 했다.
2. 다음 작업 승인 시 production/candidate 경로·원시측정정의·지도표시 미검증·비정규운행일 제외 미실행을 먼저 기억한다.
3. 제안된 smooth+pool 조합이나 가중치 탐색은 별도 실험이다. 실제피크값으로 맞추지 않고 같은 연산예산·누수없는 날짜검증을 유지한다.
4. 모델을 바꾸려면 별도후보생성→원시보존/물리잔차/날짜검증→한계보고를 거친다. 낮은 내부loss만으로production교체나실제정확도완료를 선언하지 않는다.
5. 과거 문서를 근거로60000행·12일·더미웹·JSON변환미확인·물리제약충족·Naver·ONNX완료로 되돌리지 않는다.
