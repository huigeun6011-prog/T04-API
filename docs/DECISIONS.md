## D-003: 시간대별 운영하는 지하철 수 계산법

- 결정: 열차 시각표를 바탕으로 각 열차의 운행 계획을 추측, 시간대별로 분류.
- 근거
  -- 1. 물리적으로, 두 대 이상의 대전 지하철은 같은 방향으로 동시에 운행될 수 없음.
  -- 2. 시계열 순으로 판단하였을 때, (n)번째 역에서 (x)분에 출발한 열차와 (n+1)번째 역에서 (x+k)분에 출발한 열차는, 정황상 동일한 열차라고 판단할 수 있음. (단, 1 ≤ k ≤ 4)
  -- 3. 열차별 계획된 운행시간을 추출해냈으니, 이를 바탕으로 한 시간 구간으로 운행되고있는 열차의 수를 계산할 수 있음.
- 결과
  -- 1. 열차별로 몇 시에 어느 역에 정차하는지 계산됨.
  -- 2. 시각 별로 운행되는 열차의 수와 방향이 계산됨.
- 한계
  -- 1. 기존 열차들의 역간 시간을 바탕으로, 종착역 도착 시간은 예측시간으로 계산됨. (종착역은 열차 시각표에 표시되지 않음)
  -- 2. 시각표를 바탕으로 역산된 결과임.

## D-009: 열차 계수 방식은 복원 가능성을 먼저 검증한 뒤 쓴다

- 결정: 열차마다 "얼마나 붐비는가" 계수를 변수로 두는 방식(모든 역에서 같은 열차는 같은 계수)을 쓰기 전에, 합성 자료로 이 계수가 시간별 합계만으로 복원되는지 먼저 확인한다. 복원되면 실제 평일 자료에 적용하고, 그다음에 환승 없는 다른 지하철의 실측 자료로 검증할지 정한다. (2026-11-17)
- 근거: 사용자 진술. 열차별 편차를 사람이 가정(예: 출퇴근에 가까울수록 붐빔)으로 정하지 않고, 최적화 결과로 해석되길 원한다.
- 결과: 합성 자료 실험은 선언한 기준으로 실패했다(E-18). 목적지 분포를 알고 잡음이 없을 때만 복원되고, 잡음 2%나 목적지 미지에서는 실패했으며 대조군에서 가짜 패턴이 생겼다. 따라서 정규화 없는 자유 w를 실제 평일에 적용하지 않는다. 추가 시험(E-19)에서 저차원 w + 여러 날 합치기는 목적지 분포를 밖에서 고정할 때에 한해 부드러운 출퇴근 패턴을 30분 해상도로 복원했지만, 열차별 복원과 목적지 분포 동시 추정은 실패했다. 다른 지하철 자료 검증은 이 결과를 보고 다시 정한다. 상세는 [EXPERIMENTS](EXPERIMENTS.md) E-18.
- 한계: 같은 열차가 모든 역에서 같은 계수를 갖는다는 것 자체가 구조 가정이다. 합성 실험은 수학적 복원 가능성만 보여 주고 실제 행동과 맞는지는 보여 주지 못한다.

## D-014: 최대 도보 시간과 도보 후보 상한

- 결정: 추천 요청에 `max_walk_minutes`(선택, 1~240, 화면 기본 15분, "제한 없음"은 값을 보내지 않음)를 추가한다. 열차를 타지 않는 도보 후보(출발 역과 같은 역 생활권)는 추정 도보 시간이 이 값 이하일 때만 후보가 된다. 도보 시간 = 직선거리 x 1.3(우회 계수) / 4.5km/h. 도보 후보가 목록을 채우지 않도록 결과의 도보 후보는 `limit`의 1/3까지만 먼저 담고, 자리가 남을 때만 나머지 도보 후보로 채운다(원래 순위 유지). 점수 계산은 그대로이며 점수 정규화에 쓰는 후보 모음에서 조건에 맞지 않는 도보 후보가 빠진다. (2026-11-17)
- 근거: 사용자 요청. 가까운 도보 후보(중립 점수)가 상위를 채워 멀리 있는 열차 이용 후보가 밀리는 문제.
- 결과: 15분이면 직선 약 0.87km 이내. 단일 시간 실험(7시, limit 50)에서 도보 후보 수는 5분 3개, 15분 9개, 제한 없음 16개(상한)였다. 도보 후보에는 `walk_minutes` 필드가 붙는다.
- 한계: 직선거리 어림이라 실제 길, 신호, 경사, 하천을 반영하지 않는다. 4.5km/h와 1.3은 정당화된 측정이 아닌 작업 가정이다. 열차를 이용하는 후보의 승차역까지·하차역에서의 도보는 이 한도로 걸러지지 않는다. 도보 후보 상한 1/3은 임의 값이다.

- 정정(2026-11-18, D-020): 도보 한도는 이제 걷는 시간의 합(승차역까지 + 하차역에서, 열차 없이 걸으면 곧바로 걷는 시간)에 모든 후보(열차 이용 포함)에 적용된다. 위 "열차를 이용하는 후보의 승차역까지·하차역에서의 도보는 걸러지지 않는다"는 한계는 해소됐다. 측정(출발지 대전역 근처, 7~9시, 2026-10-21): 한도 10분이면 결과의 걷는 합계 최대 10분(이전에는 열차 후보의 걷는 시간이 56~78분인 것이 47/50), 20분이면 최대 20분, 한도 없음이면 최대 97분.

## D-015: 목적지는 큰 핀으로 표시하고 정보 카드는 경로 반대쪽에 둔다

- 결정: 선택한 장소에 다른 장소의 작은 점과 구별되는 빨간 핀을 경로 위에 그린다. 정보 카드는 경로가 들어오는 방향(마지막 구간의 출발점에서 목적지로 가는 방향)의 반대쪽(북/남/동/서 중 하나)에 두고 주소 줄을 빼 작게 만든다. 지도 시점 조정(`ensureVisible`)은 핀·카드·출발지·승하차역의 화면 픽셀 영역을 계산해, 이미 모두 보이면 그대로 두고, 아니면 들어갈 때까지만 축소한 뒤 가장 적게 평행이동한다(확대 없음). (2026-11-17)
- 근거: 사용자가 목적지가 작은 점뿐이라 잘 안 보이고 카드가 경로를 가린다고 함.
- 결과: 12곳 이상의 장소(북·남·동·서 카드 위치, 도보 직행·지하철 경로)에서 핀과 카드가 지도 칸 안에 들어오는 것을 브라우저에서 확인했다. 지도 칸 크기가 바뀐 뒤에는 카카오 `relayout()`을 먼저 호출해야 경계가 맞다.
- 한계: 카드 방향은 마지막 구간의 직선 방향만 보므로 지하철 노선이나 다른 마커와 겹칠 수 있다. 지도가 아주 작으면 모두 보이게 축소하다 한계 레벨에서 멈춘다.

## D-019: 시간 막대는 순위를 바꾸지 않고 선택한 장소의 시간 정보만 바꾼다

- 결정: "언제 가면 한산할까" 막대를 누르면 서버 재순위 없이 브라우저에서만 처리한다. 목록의 장소와 순서는 그대로 두고, 선택한 장소의 행(출발 시각·예상 재차 명·추천점수·작은 막대)만 `matrix`의 그 시간 칸 값으로 바꾸며 행에 "N시 기준" 표시를 단다. 칸 값이 비어 있으면 "그 시간에는 맞는 열차 없음 / 열차 없음"으로 표시한다. "장소별 최적 시간" 버튼은 보던 시간을 해제해 그 장소의 원래(최적) 값으로 되돌린다. 다른 장소를 고르면 보던 시간이 초기화된다. 출발지 변경 자동 재검색(D-016)이나 새 검색 뒤에는 같은 장소가 그대로 선택돼 있고 그 시간이 새 `matrix`에 있을 때만 보던 시간을 유지한다. 선택한 장소에 시간별 값(상위 15곳 `matrix` 행)이 없거나 도보 후보면 막대는 눌리지 않고 안내만 보인다. 접근성: 눌린 막대 `aria-pressed`, 갱신 내용은 `aria-live="polite"` 영역(`#viewStatus`)이 읽어 주고, 막대는 Enter/Space로 조작된다. (2026-11-18)
- 근거: 사용자 결정. 시간을 누를 때 목록의 장소가 함께 바뀌면 혼란스럽다.
- 가정(미검증): `matrix` 칸에는 승·하차역이 없어 지도 경로와 행의 "A → B" 구간은 원래 선택한 승차역·하차역을 그대로 쓴다. 다른 시간에 서버가 같은 역 조합을 쓴다고 가정한 것이며, 시간마다 실제 하차역(가까운 역 기준)이 같다는 점은 코드상 같은 장소·같은 출발지라 같다고 보지만 별도 시험은 하지 않았다. 지도의 목적지 카드에는 시간·재차가 없어 바꾸지 않는다.
- 결과: 브라우저에서 세 시간(9, 15, 22시)을 눌러 목록 순서·구성이 그대로이고 선택 행의 출발·재차·점수가 API 응답 `matrix` 값(독립 호출과 일치)으로 바뀜, 초기화·다른 장소 선택·출발지 변경 자동 재검색 후 유지·빈 칸 표시를 확인했다.
- 한계: 선택한 장소의 분석 탭 프로필 강조와 지도 안내는 보던 시간을 따르지 않는다. 상위 15곳 밖의 장소는 시간별 값이 없다.

## D-020: 걷는 시간 합계 한도, 소요 시간 내역, 가까운 곳 / 지하철로 멀리 탭

> 2026-11-23: 가까운 곳 / 지하철로 멀리 탭 부분(2)은 [D-028](#d-028-웹은-구체적-재차인원-대신-같은-구간의-상대-순위만-보여-준다)의 결과 목록 구조 결정으로 대체될 예정이다(구현 전). 걷는 시간 합계 한도(1)는 유지된다.

- 결정: (1) `max_walk_minutes`는 걷는 시간 합계(`walk_total_minutes` = `walk_access_minutes` + `walk_egress_minutes`)에 적용하며 한도를 넘는 후보는 점수 계산 전에 뺀다. 걷는 시간은 직선거리 x 1.3 / 4.5km/h 로 어림한 추정치이고(격자·택시 거리 보정 없음) 화면에는 항상 "추정"을 붙인다. 후보마다 `walk_access_minutes`, `walk_egress_minutes`, `walk_total_minutes`, `ride_minutes`(열차 출발·도착 시각 차, 24시 이후 표기·자정 넘김 처리), `total_minutes`(= 걷기 합계 + 지하철, 대기·환승 시간은 넣지 않음)를 준다. 카드는 "걷기 6분 + 9분 = 15분 · 지하철 22분 · 총 37분 (추정)"으로 쓴다. (2) 결과를 총 소요 시간 `NEAR_MAX_MINUTES = 30`분(서버 `prediction_api.py`의 상수)으로 가까운 곳(`near`, 열차 없이 걷는 후보 포함)과 지하철로 멀리(`far`)로 나눠 한 응답에 함께 돌려주고(`results_near`, `results_far`, 항목마다 `group`, 기존 `results` = 둘을 이은 목록), 화면은 탭으로 보며 탭 전환은 브라우저에서만 처리한다(서버 재순위 없음). 기본 탭은 가까운 곳이고 탭에 개수를 보이며(한 그룹이 `limit`(50)을 넘어 잘리면 "50+"), 비어 있는 탭은 안내만 보이고 자동으로 옮기지 않는다. (2026-11-18)
- 근거: 사용자 결정. 시간 범위 필터로 나누면 "최대 60분이면 된다"는 사람에게 짧은 이동이 가려진다. 걷는 시간 합계 한도가 없으면 걷기만 한 시간이 긴 열차 후보가 도보 한도 10분에도 결과를 채웠다.
- 점수 처리: 거리·재차 정규화(최댓값)는 그룹 안에서 따로 하고(그룹은 후보 단위로 정함) 같은 장소는 그룹 안에서 묶어 최고 점수 하나만 둔다. 그래서 점수는 그룹 안에서만 비교할 수 있다. 같은 장소가 시간에 따라 30분 경계의 양쪽에 걸리면 두 탭에 모두 나올 수 있다(탭 안에서는 중복 없음). "거리 비중" 슬라이더는 멀리 탭에서도 그대로 두되, 그 탭에서는 "이 탭 안 장소끼리의 상대 거리"라고 탭 설명과 도움말에 적었다. 열차 없이 30분 넘게 걷는 후보(한도를 늘렸을 때)는 멀리 탭에 들어가며 이름과 달리 지하철을 쓰지 않는다. 시간 막대(matrix)·히트맵은 현재 탭의 행만 쓰고, 출발지 변경 자동 재검색은 탭을 유지한다.
- 30분 경계는 임의의 값이다: 바꾸려면 `prediction_api.py`의 `NEAR_MAX_MINUTES`를 고치고, 화면 문구(app.js의 `renderGroupTabs`, `renderRecommendations` 안내의 "30분")도 함께 고친다(문구는 아직 숫자를 직접 쓴다).
- 결과: 한도 10/20/없음에서 모든 후보의 걷기 합계가 한도 이하임을 확인, 가까운 곳은 총 30분 이하·멀리는 30분 초과를 확인, 카드의 걷기·지하철·총 분은 직선거리로 직접 계산한 값과 일치함을 확인했다.
- 한계: 걷는 시간이 직선거리 어림이라 실제와 다를 수 있다(실제 경로는 카카오맵 링크, D-012). 대기·환승 시간은 총 소요에 들어 있지 않아 실제 총 시간은 더 길다.

## D-028: 웹은 구체적 재차인원 대신 같은 구간의 상대 순위만 보여 준다

## D-029: 모델 소개는 방문자가 사이트 안에서 이해할 수 있게 설명한다

- 결정(2026-11-23, 사용자 승인): 문장별 E-/D- 식별자·저장소 문서 경로 참조를 사용자 화면에서 제거한다. 기본 설명은 무엇을 알려 주는지, 계산 과정, 확인한 결과와 한계 순서로 두고 개발 과정과 기술 설명은 선택해서 펼쳐 본다. 전문 용어는 쉬운 말로 먼저 설명하고 원하는 사람이 뜻·예시·기술 설명을 확인할 수 있게 한다.
- 단계 구분: OD는 승하차 합계·시간표에서 학습용 추정값을 만드는 단계이고 HGB는 이를 학습해 서비스 예측을 내는 단계다. 학습용 추정값을 실측 정답으로 부르지 않는다. 이전 배분 방식 대 OD는 추정값 생성 방법 선택, OD 직접 계산 대 HGB 예측은 두 단계의 결과 점검으로 구분한다. Adam은 이전 방식 안의 최적화 알고리즘이지 HGB의 대안 모델 이름이 아니다.
- 평가 설명: 대전 피크 시간 순위는 OD 직접 계산과 HGB 예측 모두 1위 14/18·상위 3위 18/18이지만 전체 예측 일치나 독립 검증을 뜻하지 않는다. 학습일 포함·사례 반복·한산한 시간 미검증을 유지한다. HGB의 열차 평가는 같은 시간 예측을 그 시간 모든 열차에 붙인 결과라 개별 열차 식별 능력으로 해석하지 않는다. 항저우 비교 기준은 승객 태그와 추정 시간표로 구성한 것으로 독립 실측 정답이 아니다.
- 표: 개발 과정 표의 ID 열을 제거한다. 짧은 상태·제목·숫자는 한 줄 유지, 긴 내용은 설명 칸에서 줄바꿈한다. 좁은 화면에서는 페이지 전체가 아니라 표 컨테이너 안에서 가로 스크롤한다.
- 작업 범위: 모델 소개 HTML·해당 CSS와 관련 문서. 예측 모델·API·학습 데이터는 변경하지 않는다. 검증 결과는 ROADMAP 완료 기록에 남긴다.

## D-030: 현재 학습 모델을 JavaScript로 내보내 별도 정적 웹에서 실행한다

- 결정(2026-11-23, 사용자 승인): YML이나 상시 Python 서버 없이 운영할 정적 웹을 별도로 만든다. 기존 Python 파일은 갱신하지 않는다. 현재 서비스에서 필요한 계산만 JavaScript로 옮기고, 학습된 모델과 필요한 데이터를 내보내는 코드를 작성한다. OD 재계산·모델 재학습은 작업 범위가 아니다.
